## 4. Исторический контекст — не выдавать за текущую проверку

Следующие сведения присутствуют в доступной истории проекта/предыдущих сессий, но в этой документальной сессии не перепроверялись по текущему коду и артефактам:

- Ранее отмеченная рабочая точка веб-интерфейса: ветка `candidate/CARD111-ui-2xN-20261006`, коммит `a1085aa7799998b80946808247775c9b4f5f0df3`.
- Ранее упоминались restore-точки `restore/CARD111-ui-before-fixes-20261006` (`41af99d9e0407d24706d99276d28aae447d5b5be`) и `restore/CARD111-CORE-1.7.9.7-20261006` (`5e77307ed62984093c23cc6a25295105abe2c8b8`).
- Ранее сообщалось о корректировке пропорций карточек, размера центрального заголовка, сохранения карточек, импорта/восстановления данных, предпросмотра редактора и CSS.
- Ранее сообщалось, что QR-коды «Пятёрочка» и «Магнит» были испытаны на кассе, но они могут быть временными и истекать.
- Существующий журнал инцидентов фиксирует APK Flet API regression и Web scanner syntax regression. В нём для APK FIX3 указан статус UNVERIFIED без Android E3; для web FIX указан E2 parse, но live/device E3 отсутствует на момент записи. Текущий статус этих функций требуется сверить заново перед работой над ними.

Исторические данные — ориентир для поиска, не доказательство того, что соответствующая ветка/сборка является текущей или что поведение сейчас исправно.

## 5. Обязательные ограничения и рабочий порядок

- Следовать иерархии: сохранность данных → явные требования пользователя → проектная инструкция и активный CORE → проверенные факты → рекомендации → гипотезы.
- До изменений проверить HEAD, базу/ветку, файлы и артефакты; фиксировать исходную точку.
- Минимальный контур: один логический change → проверка → reverse-diff/регрессия → фиксация → обновление WORKLOG и HANDOFF.
- Не удалять и не перезаписывать пользовательские данные/историю без разрешения и плана восстановления.
- Не объявлять APK или web-релиз готовым без соответствующих проверок в целевой среде.
- Не считать несколько повторений утверждения независимыми доказательствами.
